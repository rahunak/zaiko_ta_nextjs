# Зайко Татьяна — короткая инструкция

## Что это

Сайт мастера по бровям и ресницам (`zaiko.by`) и закрытая админка `/admin` для работы с записями.
Клиентки смотрят услуги, работы и отзывы на сайте; мастер ведёт записи в админке, а записи
синхронизируются с DIKIDI — кабинетом, куда приходит онлайн-запись.

## Вход

- Адрес: `/admin/login`. Логин и пароль выдаёт владелец (хранятся в базе, пароль — в виде хэша).
- Сессия живёт 7 дней, «Выйти» — в шапке админки.

## Запись клиента

1. Открыть `/admin` — форма «Новая запись».
2. Указать имя, телефон (`+375 XX XXX-XX-XX`), услугу, дату и время, при необходимости комментарий.
3. Галочка «Отправить в DIKIDI» — запись сразу создаётся в кабинете. Без галочки остаётся только в админке.

Ограничения DIKIDI: запись принимается только в рабочее окно мастера и без пересечения с другой
записью. Если время не подходит, запись сохранится в локальной базе, а причина появится в статусе —
время нужно поправить и отправить ещё раз.

## Статусы записи

| Статус | Значение |
|---|---|
| в DIKIDI | запись есть в кабинете, всё синхронизировано |
| только в БД | в DIKIDI не отправляли или время вне графика |
| не отправлено | DIKIDI отказал — причина в подсказке при статусе |

## Расписание

`/admin/schedule` — день или неделя, дата выбирается в календаре. В списке видны и записи админки,
и записи из DIKIDI (клиент записался сам или мастер завёл в кабинете).

У каждой записи есть кнопки:

- **Изменить** — форма правки: клиент, телефон, услуга, дата, время, комментарий. Галочка
  «Обновить запись в DIKIDI» обновляет ту же запись в кабинете, дубль не создаётся.
  Если новое время вне графика, в DIKIDI остаётся прежняя версия, а статус станет «не отправлено».
- **Отменить** — запись убирается из расписания и удаляется в DIKIDI. В базе она сохраняется
  для истории. Если DIKIDI не принял удаление, запись остаётся, а причина показывается в баннере.

## Если что-то не загрузилось

- «Записи DIKIDI не загружены» — админка не смогла прочитать журнал, показаны только свои записи;
  в баннере написана причина.
- «Сессия DIKIDI истекла» — нужно обновить доступ к кабинету (токен или логин и пароль DIKIDI).
- Отменённую запись нельзя открыть повторно: она осталась в базе, но в расписании её нет.

## Telegram: два бота

В проекте два разных бота, и они не взаимозаменяемы:

| Бот | Кому пишет | Что нужно настроить |
|---|---|---|
| `zaiko_ta_admin_bot` | мастеру: новая запись, «через час приём» | токен + chat_id мастера |
| `zaiko_ta_bot` | клиентам: напоминание о визите | токен + имя + вебхук |

Причина разделения: Telegram не даёт боту написать человеку, который не начинал диалог
именно с этим ботом. Клиент подписан на `zaiko_ta_bot` — значит и напоминание должно
уходить от него, а не от админского.

### Админский бот (мастеру)

1. Мастер открывает `zaiko_ta_admin_bot` в Telegram и нажимает **Start** — без этого бот
   не сможет написать первым (ошибка `chat not found`).
2. Узнать свой chat_id: написать боту `@userinfobot` — он пришлёт число вида `5151069944`.
3. В окружении сервера (Vercel → Environment Variables):
   - `TELEGRAM_MASTER_BOT_TOKEN` — токен `zaiko_ta_admin_bot` от `@BotFather`;
   - `TELEGRAM_MASTER_CHAT_ID` — числовой chat_id мастера; несколько — через запятую.
4. Вебхук админскому боту **не нужен**: он только отправляет сообщения.

### Бот напоминаний клиентам

1. В окружении сервера:
   - `TELEGRAM_CLIENT_BOT_TOKEN` — токен `zaiko_ta_bot` от `@BotFather`;
   - `TELEGRAM_CLIENT_BOT_USERNAME=zaiko_ta_bot` — имя без `@`, из него собирается
     кнопка «Получить напоминание в Telegram» на `/book`;
   - `TELEGRAM_CLIENT_WEBHOOK_SECRET` — любая случайная строка (необязательно, но рекомендуется);
   - `CRON_SECRET` — секрет для `/api/cron/dispatch` (без него эндпоинт отвечает 503).
2. Один раз зарегистрировать вебхук на публичный HTTPS-адрес:

```bash
curl "https://api.telegram.org/bot<ТОКЕН zaiko_ta_bot>/setWebhook?url=https://zaiko.by/api/telegram/webhook&secret_token=<СЕКРЕТ>"
```

Проверка: в ответе `{"ok":true,...}` и `pending_update_count: 0` в `getWebhookInfo`.

3. Тик напоминаний — `/api/cron/dispatch` (старый `/api/cron/reminders` — алиас). На Vercel
   встроенный cron на Hobby запускается раз в сутки с точностью ±59 минут, а `setInterval`
   замораживается после ответа, поэтому расписание живёт снаружи: cron-job.org (5 минут) и
   QStash (15 минут). Пошаговая настройка — раздел «Расписание напоминаний» ниже.

### Что видит клиент

- `/start` с меткой записи — «Напоминание включено» и данные визита; если до визита меньше часа,
  напоминание приходит сразу.
- `/start` без метки — подсказка, как записаться.
- Регистрация не обязательна: без Telegram запись работает как раньше.

### Настройки онлайн-записи (админка → «График»)

- **Минимум часов до записи** — слоты раньше этого срока клиентам не показываются (по умолчанию 2 ч,
  `0` — без ограничения).
- **Буфер между процедурами, мин** — время на уборку и подготовку после каждой записи (по умолчанию 10).
- **Дублировать онлайн-записи в DIKIDI** — прежний глобальный флаг.

## Каналы записей

В базе у записи есть поле `source`:

| Значение | Откуда запись |
|---|---|
| `online` | клиент записался сам через `/book` |
| `admin` | мастер создал вручную в админке |
| `dikidi` | пришла из журнала DIKIDI |

В расписании канал виден в бейдже («онлайн · в БД», «админка · в DIKIDI», «DIKIDI»).

## Согласие на обработку данных

Ссылка в футере ведёт на `/privacy` — там опубликован документ о сборе и обработке данных
(оператор, какие данные, цели, сроки, права, контакты). Текст типовой: при необходимости
мастер согласует формулировки с юристом, структура документа уже на месте.

## Расписание напоминаний

Напоминания — это очередь в таблицах `reminders` и `cron_runs`. Планировщик ничего не
помнит: его задача — раз в несколько минут дёрнуть один URL. Всё состояние в базе, поэтому
смена планировщика не трогает код.

### Почему снаружи

- Vercel Cron на Hobby: раз в сутки, точность ±59 минут, повторов нет. Для «за час до визита»
  не подходит.
- `setInterval` внутри Next.js на Vercel замораживается после ответа — это мёртвый код.
- Supabase `pg_cron` живёт в базе: если проект засыпает, тик умирает вместе с очередью.
  Поэтому он годится только как третий, резервный триггер (см. ниже), а не как основной.

### cron-job.org — основной триггер

1. Регистрация на cron-job.org (бесплатно, без карты).
2. **New cronjob**:
   - URL: `https://zaiko.by/api/cron/dispatch?source=cronjob`
   - Schedule: **every 5 minutes**
   - Method: `GET`
   - Custom header: `Authorization: Bearer <CRON_SECRET>`
   - включить e-mail-уведомление о сбоях (Notifications → «on failure»)
3. Сохранить и дождаться первого запуска. В нём видно код ответа и тело
   (`{"ok":true,"run":123,"picked":0,"sent":0,...}`).

Ограничения сервиса: ответ должен уложиться в 30 секунд, история — последние 50 запусков,
после 25 ошибок подряд задание отключается (поэтому e-mail-уведомление обязательно).

### Upstash QStash — независимый второй триггер

Бесплатно: 1000 сообщений в день, **10 активных расписаний**, разрешение 1 минута.
Тик каждые 15 минут — это 96 сообщений в день.

- Destination: `https://zaiko.by/api/cron/dispatch?source=qstash`
- Cron: `*/15 * * * *`
- Заголовок: `Upstash-Forward-Authorization: Bearer <CRON_SECRET>` (QStash передаёт только
  заголовки с префиксом `Upstash-Forward-`).

Токен `QSTASH_TOKEN` создаётся автоматически вместе с QStash и лежит в консоли:
вкладка **QStash → Quickstart**. Для расписания через дашборд он не нужен — дашборд уже
авторизован; токен нужен только для API/SDK/CLI. Не путать его с `CRON_SECRET`: в
`Upstash-Forward-Authorization` идёт секрет сайта, иначе эндпоинт ответит `401`.
Первый запуск расписания может появиться не сразу — до 60 секунд.

Оба планировщика могут работать одновременно: строки захватываются через
`for update skip locked`, поэтому каждое напоминание уходит один раз.

### pg_cron + pg_net — третий триггер внутри Supabase

Страховка на случай, когда внешние сервисы молчат: cron-job.org отключил задание после
серии ошибок, у QStash кончилась квота или аккаунт заблокирован. Живёт в самой базе,
внешних аккаунтов не требует.

Настройка одной командой. Нужен **direct-URL** Supabase; если он не подключается
(`ECONNREFUSED` на адресе `2a05:…` — direct-хост только IPv6, а в сети нет IPv6), берите
**session pooler** `...pooler.supabase.com:5432`: DDL и задания cron через него создаются.
Transaction pooler `:6543` не подходит. Расширения можно включить и в Dashboard →
Database → Extensions, но скрипт делает это сам:

```bash
# direct-URL или session pooler (:5432)
DATABASE_URL="postgres://postgres.<ref>:<пароль>@aws-1-<region>.pooler.supabase.com:5432/postgres" \
CRON_SECRET="<CRON_SECRET>" bun run db:cron
```

Что делает скрипт: проверяет наличие `pg_cron`/`pg_net` и таблицы `reminders`,
включает расширения, пересоздаёт задание `zaiko-reminders-pgnet` с расписанием
`*/10 * * * *`, которое через `pg_net.http_post` дёргает
`/api/cron/dispatch?source=pg_cron` с тем же `Authorization: Bearer`.

```bash
bun run db:cron --dry-run   # показать команду задания, ничего не меняя
bun run db:cron --remove    # удалить задание
```

Ограничения, которые надо знать:

- **Не заменяет внешние триггеры.** Задание выполняется, пока жива база; если проект
  на паузе, тикать некому — но и очередь в этот момент недоступна.
- **Нет ретраев.** `succeeded` в `cron.job_run_details` значит «запрос поставлен в очередь
  pg_net», а не «эндпоинт ответил 200». Ответ и код смотреть в `net._http_response`
  (хранится 6 часов):
  `select status_code, error_msg, created from net._http_response order by created desc limit 5;`
- **Секрет лежит в `cron.job`** открытым текстом — как и в настройках cron-job.org. Доступ
  к таблице есть только у владельца базы, но это надо помнить при смене пароля/секрета.
- **Смена `CRON_SECRET`** требует перезапуска `bun run db:cron`: старое задание хранит
  старый заголовок.
- **Отключение `pg_cron`** (`drop extension`) удаляет задание навсегда.

### Что делает тик

1. Пишет запуск в `cron_runs`; если прошлый успешный тик был больше 2 часов назад — сообщает мастеру.
2. Возвращает в работу строки, зависшие в `claimed` дольше 10 минут.
3. Создаёт строки по будущим записям и сдвигает `due_at`, если запись перенесли.
4. Отменяет строки отменённых и прошедших визитов.
5. Захватывает пачку (≤20) и отправляет: мастеру — админский бот, клиенту — `zaiko_ta_bot`.
6. Ошибки: 5xx/сеть — повтор `1м → 5м → 15м → 60м`; 429 — пауза по `retry_after`;
   403/`chat not found` — `failed` и отвязка `client_chat_id`.

### Проверка вручную

```bash
curl -H "Authorization: Bearer $CRON_SECRET" https://zaiko.by/api/cron/dispatch
# {"ok":true,"run":123,"source":"external","picked":0,"sent":0,"failed":0,...}
```

Без заголовка — `401`, без `CRON_SECRET` в окружении — `503`.

### Страница «Напоминания» (`/admin/reminders`)

- счётчики по статусам (`ожидает`, `в работе`, `отправлено`, `ошибка`, `пропущено`, `отменено`);
- «последний успешный тик»: если старше 30 минут — красным;
- список ошибок и пропусков по будущим визитам с причиной и кнопкой «Переотправить»;
- «Прогнать сейчас» — тот же тик, вручную (полезно после починки или если cron молчит);
- журнал последних 20 тиков с источником и счётчиками.

### Если напоминания не приходят

1. Открыть `/admin/reminders`: есть ли свежий тик.
2. Тита нет — проверить задания на cron-job.org/QStash и внутреннее `pg_cron`
   (`select jobname, schedule, active from cron.job;`): включено ли, какой код ответа,
   тот ли `CRON_SECRET` (кавычки и пробелы в env ломают заголовок).
3. Тик есть, но строки в `ошибка` — прочитать `last_error`:
   `bot was blocked by the user` / `chat not found` значат, что клиент заблокировал бота
   или удалил чат; повторять бесполезно.
4. Клиент не нажимал кнопку — строки `пропущено` с причиной `no_subscription`.
   После повторного `/start` напоминание отправится сразу, если срок уже наступил.
5. Записи в `пропущено` с причиной `visit_passed` — визит прошёл, пока тик не работал;
   напоминание не отправляется, чтобы не писать «ждём вас завтра» через два дня.

### Диагностика одной командой

```bash
bun run scripts/telegram-check.ts          # проверки без отправки
bun run scripts/telegram-check.ts --send   # + тестовое сообщение мастеру
```

Скрипт проверяет токены, вебхук клиентского бота, chat_id мастера, наличие таблиц очереди,
последний успешный тик и сколько строк ждут отправки. Ненулевой код возврата — есть проблемы.

Отдельно: на **админском** боте вебхука быть не должно. Если `getWebhookInfo` показывает URL,
снимите его — иначе `/start` мастера уйдёт в обработчик клиентского бота:

```bash
curl "https://api.telegram.org/bot<ТОКЕН zaiko_ta_admin_bot>/deleteWebhook"
```
