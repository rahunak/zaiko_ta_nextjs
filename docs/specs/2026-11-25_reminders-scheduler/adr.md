# ADR 2026-11-25-01: планировщик напоминаний вынесен из Vercel, очередь — таблица в Postgres

**Статус:** принято и реализовано 2026-11-25 (итог — `spec.md` §10) · **Проект:** `zaiko_ta/zaiko_ta_nextjs`
· **Контекст:** Vercel Hobby, Supabase Free, один мастер, ~30 записей в неделю

## Контекст

Клиент включает напоминание кнопкой на `/book` (deep-link `?start=<client_token>`), но отправлять
его нечем: `setInterval` в `instrumentation.ts` на serverless не живёт, а cron Vercel Hobby
запускается раз в сутки с точностью ±59 минут и без повторов. Напоминание «за час до визита»
на такой платформе невозможно, а не «медленно».

Проверенные ограничения бесплатных планов (2026-11-25):

| Сервис | Что даёт | Ограничение, важное здесь |
|---|---|---|
| Vercel Cron (Hobby) | 100 заданий на проект | раз в сутки, ±59 мин, без повторов ([docs](https://vercel.com/docs/cron-jobs/usage-and-pricing)) |
| cron-job.org | бесплатно, без лимита заданий (fair use), интервал от 1 минуты, свои заголовки, история 50 запусков, e-mail-алерты | 30 с на ответ, 64 КБ ответа, без повторов, отключает задание после 25 ошибок подряд ([FAQ](https://cron-job.org/en/faq/)) |
| Upstash QStash | 1000 сообщений/день, 3 ретрая с backoff, DLQ и логи 3 дня, разрешение 1 минута | **10 активных расписаний** на Free; квота тратится по тикам, а не по напоминаниям ([pricing](https://upstash.com/pricing/qstash)) |
| Supabase pg_cron | планировщик внутри базы | Free-проект засыпает после 7 дней низкой активности; нет ретраев и видимости |
| GitHub Actions | репозиторий уже есть | минимум 5 минут, авто-отключение scheduled workflow через 60 дней без активности |
| Cloudflare Workers | 100k запросов/день, cron | ещё одна платформа и деплой ради одного `fetch` |

## Решение

1. **Единственный источник истины — Postgres.** Напоминание материализуется в строку `reminders`
   с `due_at`, статусом, `attempts` и `next_attempt_at`. Планировщик не хранит состояния: его
   задача — раз в N минут дёрнуть `GET /api/cron/dispatch`.
2. **Строки создаёт сам тик** (`insert … select from appointments … on conflict do update`), а не
   транзакция брони. Смена времени и отмена подхватываются автоматически, существующие записи
   бэкфиллятся, нет пяти мест, где можно забыть хук.
3. **Захват пачки** — `select … for update skip locked` в CTE и `update … returning`. Два
   одновременных тика берут разные строки; уникальность `(appointment_id, kind)` закрывает
   дубли на уровне данных.
4. **Ретраи, backoff и dead-letter — в таблице.** Так любой источник тика (cron, QStash, curl,
   кнопка в админке) даёт одинаковое поведение, а смена планировщика не трогает бизнес-логику.
5. **Два независимых внешних триггера:** cron-job.org каждые 5 минут (основной, e-mail-алерты)
   и QStash каждые 15 минут (второй, 96 сообщений/день из 1000). Система корректна и с одним
   из них — второй нужен только на случай молчания первого.

## Следствия

**Плюсы.** 0 ₽/мес; напоминание уходит по расписанию, а не «когда кто-то откроет админку»;
любой пропуск догоняется; видно, что сломалось (статусы, `last_error`, журнал тиков, страница
`/admin/reminders`); смена планировщика — правка одного URL.

**Минусы и цена.** Строка появляется в базе в течение ≤5 минут после записи (а не в момент
брони) — для UI это незаметно, для отладки важно помнить. Нужны два бесплатных аккаунта.
Остаётся узкое окно дубля, если процесс умрёт между успешным `sendMessage` и записью
`telegram_message_id`: Telegram не поддерживает ключ идемпотентности. Редкий дубль с датой и
временем в тексте признан меньшим злом, чем пропущенное напоминание.

**Что не делаем и почему.** Не переезжаем на `booking`/`client`/`tg_subscription` — в проекте
уже есть `appointments` с именем, телефоном, `client_token` и `client_chat_id`; новая модель даёт
чистоту схемы, но не влияет на доставку и стоит недель работы. Не заводим Redis «для очереди»:
очередь — таблица, состояние напоминания терять нельзя. Не делаем отдельный watchdog-эндпоинт:
тик сам замечает разрыв > 2 часов в `cron_runs` и пишет мастеру, а падение самого планировщика
видно по e-mail cron-job.org. Не используем `delivery`/`consent_log` в v1 — один канал, один
получатель; журнал согласий — отдельная юридическая задача.

## Альтернативы

- **pg_cron + pg_net** — планировщик умирает вместе с базой на Free и не даёт ни ретраев, ни
  видимости. Годится как третий, резервный триггер, но не как основной.
- **GitHub Actions** — 5 минут и тихое отключение через 60 дней без коммитов; для сайд-проекта
  это отложенная поломка.
- **Cloudflare Workers** — технически хорошо (100k/день, нулевой cold start), но это третья
  платформа и третий деплой ради одного `fetch`.
- **Vercel Cron** — раз в сутки; как единственный механизм непригоден. Может быть бесплатной
  третьей страховкой (одно задание в `vercel.json`), если захочется.

## Проверка решения

Решение считается принятым, когда: (1) тик отправляет напоминание клиенту за час до визита и
мастеру — за час; (2) два параллельных тика не дают дублей; (3) отмена/перенос записи не
отправляют устаревшее напоминание; (4) в `/admin/reminders` видно последний тик и ошибки;
(5) смена URL планировщика не требует изменений в коде.
