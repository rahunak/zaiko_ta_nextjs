## Этап 2. Отправка с классификацией ошибок

**Цель:** отличать «повторить» от «повторять бесполезно», знать `retry_after` и `message_id`.
**Файлы:** `lib/telegram.ts`.
**Критерии:** 6. **Решение:** D8.

- [x] Тип результата: `{ ok: true, messageId } | { ok: false, retryable, retryAfterSec?, description }`
- [x] `sendTelegramToChatDetailed(chatId, text)` и `sendTelegramMessageDetailed(text)` (мастер — всем chat_id, ok только если все)
- [x] Маппинг: 2xx → ok; 429 → retryable + `parameters.retry_after`; 5xx/сеть/таймаут → retryable;
      400/403 с `bot was blocked`, `chat not found`, `user is deactivated`, `PEER_ID_INVALID` → permanent;
      прочие 4xx → permanent
- [x] Сохранить булевы обёртки `sendTelegramMessage` / `sendTelegramToChat` (их зовут уведомление
      о записи, DIKIDI-синк, вебхук) — сигнатуры не меняются
- [x] Разбор ответа с `escapeHtml` не ломать (HTML в тексте остаётся)

**Проверка:** `npx tsc --noEmit`; отправка на мастерский chat → `ok` + `messageId`; на
несуществующий chat → `retryable:false` + `description`.
**Stop-кран:** Telegram меняет формат ошибки так, что 403 не отличить от 400 → фиксируем в
`last_error` сырой ответ и считаем permanent только по коду 403.

## Этап 3. Ядро очереди

**Цель:** один идемпотентный `runDispatch`, одна функция отправки для тика и вебхука.
**Файлы:** `lib/notifications/reminders.ts` (переписать), `lib/notifications/client-reminders.ts`
(оставить тексты/константу), удалить `lib/notifications/scheduler.ts` и `instrumentation.ts`.
**Критерии:** 1, 2, 3, 4, 5, 6, 7, 8, 11. **Решения:** D2, D3, D4, D5, D9.

- [x] `REMINDER_KINDS`: `master_t60` (60 мин, админский бот), `client_t60` (60 мин, `zaiko_ta_bot`)
- [x] `runDispatch({ source })`: `cron_runs` → алерт о разрыве > 2 ч → reaper → ensure → cancel sweep
      → claim ≤20 → отправка → финализация `cron_runs`
- [x] `ensure`: `insert … select from appointments … on conflict (appointment_id, kind)
      do update set due_at = excluded.due_at where reminders.status = 'pending'` (окно 60 дней)
- [x] `cancel sweep`: `pending` + отменённая/прошедшая запись → `cancelled`
- [x] `claim`: CTE с `for update skip locked`, `attempts < 5`, `next_attempt_at <= now()`
- [x] `sendReminderById(id, source)`: перечитать запись → отмена/время/`chat_id` → отправить → статус
- [x] Backoff `1м → 5м → 15м → 60м`, на 5-й неудаче `failed`
- [x] 429: `next_attempt_at = now() + retry_after + 5 c`, пачка останавливается
- [x] 403/`chat not found`: `failed`, `appointments.client_chat_id = null`
- [x] `resetReminder(id)` и `remindersOverview()` (счётчики, последние тики, `failed`)
- [x] Удалить `setInterval`-планировщик и его регистрацию
- [x] Перестать писать `reminder_sent_at` / `client_reminder_sent_at` (колонки остаются историей)

**Проверка (локальная БД, тестовые записи создаются SQL-ом и удаляются после):**
запись T+30 мин с `chat_id` → `sent`; T+90 мин → `pending` с `due_at = starts_at − 60 мин`;
два параллельных `runDispatch` → без дублей; битый `chat_id` → `failed`; запись −3 ч → `skipped`;
отменённая → `cancelled`; `claimed_at` −20 мин → снова `pending`.
**Stop-кран:** дубль при параллельных запусках → стоп, разбор SQL захвата.
