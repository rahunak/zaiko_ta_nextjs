# Спека: отмена записи, правка записи и понятная отправка в DIKIDI

**Дата:** 2026-11-19 · **Проект:** `zaiko_ta/zaiko_ta_nextjs` · **Статус:** выполнено (итог ниже)

## Проблема

1. Клиент отказывается от записи — отменить её в админке нельзя, а мастер делает это в DIKIDI вручную.
2. Непонятно, почему запись «не отправлено». Разбор живых данных показал: DIKIDI отклоняет запись вне графика
   мастера. График мастера 3834316: **11:00–17:00**, суббота **11:00–16:00**. `2026-12-01 14:15` → `synced`,
   `2026-12-01 20:20` и `23:20` → `failed` с `{"error":1}`. В интерфейсе это выглядело как «не отправлено» без причины.
3. Опечатку в записи (время, услуга, телефон, имя) исправить нельзя: только создать новую, старые висят в списке.
4. При исправлении нужна дедупликация: правка уже отправленной записи должна обновлять её в DIKIDI, а не плодить копии.

## Кто пользователь

Мастер/владелец в `/admin`: принимает отказ по телефону или в мессенджере и хочет закрыть запись в два клика.

## Критерии приёмки

| # | Критерий (проверяемый) |
|---|---|
| 1 | В `/admin` и `/admin/schedule` у каждой локальной записи есть кнопка «Отменить»; после подтверждения запись получает `cancelled_at`, исчезает из расписания и из «последних записей», но остаётся в БД |
| 2 | Если у записи есть `dikidi_id`, отмена удаляет её и в DIKIDI (`remove-record`); сбой удаления показывается текстом и не отменяет локальную отмену |
| 3 | У записи есть форма правки: дата, время, услуга, имя, телефон, комментарий |
| 4 | Правка записи со статусом `synced` обновляет её в DIKIDI тем же `record_id` (`master-records-update`), в журнале остаётся одна запись |
| 5 | Правка/создание с галочкой «Отправить в DIKIDI» для записи без `dikidi_id` создаёт её один раз; повторное нажатие при `synced` не создаёт дубль |
| 6 | Перед отправкой читается график мастера на дату: если время вне `work_from`–`work_to` или пересекается с существующей записью, отправка не выполняется, статус остаётся `local`, в интерфейсе — причина («вне графика мастера DIKIDI 11:00–17:00») |
| 7 | В форме создания подсказка: «Если время вне графика мастера в DIKIDI, запись сохранится только в локальной БД» |
| 8 | `npx tsc --noEmit` и `npx next build` проходят; существующие записи не теряются |

## Вне scope

Уведомления клиенту (SMS/Telegram), отмена клиентом из публичной формы, повторяющиеся записи, журнал истории правок,
перенос записи drag-n-drop, работа с чужими записями (не из админки).

## Решения

1. **Отмена — мягкая**: колонка `cancelled_at timestamptz` вместо удаления строки (история и суммы сохраняются,
   `delete` в app-коде запрещён правилами).
2. **Правка — отдельная страница** `/admin/appointments/[id]` (server action `updateAppointment`), чтобы не усложнять
   список инлайн-формами.
3. **Дедупликация в DIKIDI — через `appointment_id`** в `record_save`: проверено, ответ `master-records-update`,
   запись та же. Если `dikidi_id` нет — обычное создание.
4. **Предпроверка графика** — чтение того же `journal` (уже установленная read-операция) за нужный день; проверка
   попадания в `work_from`–`work_to` и пересечения с существующими записями. Отправка вне графика не выполняется,
   чтобы не получать `{"error":1}` и не пугать владельца.
5. **Отмена в DIKIDI** — новая write-операция `remove-record` (уже добавлена и проверена живьём).

## Риски

- График мастера в DIKIDI может меняться в течение дня — предпроверка по кэшу не кэшируется, читается на каждую отправку.
- `record_save` с `appointment_id` для несуществующей записи вернёт ошибку — трактуем как «синхронизация потеряна»,
  предлагаем отправить заново как новую запись (сбрасываем `dikidi_id`).
- Отмена в DIKIDI необратима: если DIKIDI вернёт успех, восстановить запись можно только новой отправкой.

### Отклонения от плана

- Отдельного действия `resendAppointment` нет: повторная отправка — это та же форма правки с галочкой
  «Отправить запись в DIKIDI», она же обновляет существующую запись. Меньше кода, один путь.
- Причины блокировки в `lib/dikidi/availability.ts` сделаны нейтральными («Время вне графика мастера в DIKIDI
  (11:00–17:00).») — следствие объясняют сообщения интерфейса, потому что для создания это «осталось локально»,
  а для правки уже отправленной записи — «в DIKIDI старая версия».

### Как проверялось

- Живые операции DIKIDI через api-anything: создать → 12:00, обновить → 13:00 (тот же `record_id`), удалить → журнал пуст.
- Server actions — настоящими POST-формами к запущенному `next start` с серверной сессией админа (сессия создана
  временно и удалена после проверки); тестовые записи в БД (id 9, 10) удалены.
- Не проверено: ручной проход в браузере под логином/паролем владельца (доступа к паролю у агента нет).
