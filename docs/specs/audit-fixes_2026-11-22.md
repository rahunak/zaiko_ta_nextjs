# SDD: исправление замечаний аудита (сайт, админка, флоу записи)

**Дата:** 2026-11-22 · **Основание:** `docs/audit_site-admin-booking_2026-11-22.md`
**Статус:** в работе

## 1. Проблема

Аудит зафиксировал 20 замечаний. Критичное: мастер не узнаёт о новой онлайн-записи, форма
допускает дубли и двойное бронирование, сайт и `/book` показывают разные цены, успешная запись
не измеряется аналитикой, у формы нет страницы о согласии на сбор данных. Плюс набор
эксплуатационных дыр (потерянные напоминания, отсутствие проверки наложения в админке,
рестарт-зависимость расписания, rate limit, открытый cron, метаданные `/book`, служебные страницы).

## 2. Критерии приёмки

Каждый пункт проверяется отдельно; «собралось» — не проверка.

### Этап 1 — доверие и корректность (P0)

| ID | Критерий | Чем проверяется |
|---|---|---|
| A1 | После записи через `/book` уходит Telegram-сообщение мастеру: имя, телефон, услуги, дата и время (Минск), цена, номер записи. Ошибка Telegram не мешает созданию записи | запись создаётся при пустых `TELEGRAM_*` (no-op, 200/редирект); вызов обёрнут в try/catch |
| A2 | Кнопка «Записаться» во время отправки disabled и показывает «Отправляем…»; повторный тап не создаёт вторую запись | Playwright: два быстрых клика → в БД одна запись |
| A3 | Два параллельных запроса на один слот создают ровно одну запись | два одновременных POST-действия/скрипта на один слот |
| A4 | Цены и длительность услуг на `/` и гео-страницах берутся из БД; карточка услуги, которой нет в БД, не показывается; цены на `/` совпадают с `/book` | сравнение HTML `/` и `/book`; Playwright-рендер карточек |
| A5 | Опечатка «окрашивние» в названии услуги исправлена, дубль-услуга скрыта из записи (строка в БД сохраняется) | запрос к `services`; `/book` не показывает дубль |
| A6 | При открытии `/book?booked=N` в `window.dataLayer` есть событие `booking_created` с номером записи | Playwright: чтение `window.dataLayer` |
| A7 | `/privacy` открывается и содержит документ о сборе и обработке данных (оператор, данные, цели, сроки, права, контакты); ссылка в футере ведёт на неё; страница в `sitemap.xml` | curl `/privacy` (200 + текст), клик по ссылке футера, `sitemap.xml` |

### Этап 2 — клиентский сервис и админка (P1)

| ID | Критерий | Чем проверяется |
|---|---|---|
| B1 | Карточка успеха показывает дату, время, услуги и сумму записи (из БД по `booked`) | Playwright: текст карточки после записи |
| B2 | Напоминание не помечается отправленным, если Telegram вернул ошибку (повторится на следующем тике) | `sendTelegramMessage` возвращает результат; ветка ошибки покрыта кодом + прогон с неверным токеном не ставит `reminder_sent_at` |
| B3 | Ручная запись в админке не создаётся на занятое время — показывается понятная ошибка, форма сохраняет ввод | Playwright: две записи на одно время через `/admin/new` |
| B4 | Расписание обновляется без ручной перезагрузки: при возврате на вкладку/через интервал новые записи видны | Playwright: вставка записи в БД → фокус вкладки → запись в списке |

### Этап 4 — напоминание клиенту в Telegram (запрос пользователя 2026-11-22)

Сценарий: клиент записался → на карточке успеха есть кнопка «Получить напоминание в Telegram» →
открывается бот с deep-link на конкретную запись → клиент нажимает `/start` → бот привязывает
chat_id к записи и за 2 часа до визита присылает напоминание.

| ID | Критерий | Чем проверяется |
|---|---|---|
| D1 | У каждой записи есть неугадываемый `client_token`; после успешной записи показывается кнопка `https://t.me/<bot>?start=<token>`; если имя бота не настроено, кнопки нет (а не битая ссылка) | HTML `?booked=N` с `TELEGRAM_BOT_USERNAME` и без него |
| D2 | `/start <token>` привязывает chat_id к записи и отвечает клиенту подтверждением с датой, временем и услугой | POST update в `/api/telegram/webhook` → `client_chat_id` заполнен, ответ сформирован |
| D3 | За 2 часа до визита клиент получает напоминание; отметка `client_reminder_sent_at` ставится только при успешной отправке; отменённые и отправленные повторно не идут | прогон `sendClientReminders` с фейковым fetch (ошибка/успех) |
| D4 | `/start` без токена и с неизвестным/отменённым токеном — понятный ответ, данные не меняются | два POST-update |
| D5 | Понятно, как включить: регистрация вебхука и переменные окружения описаны в `docs/admin-guide.md` | чтение документа |

Требует от владельца: `TELEGRAM_BOT_TOKEN` (уже используется), `TELEGRAM_BOT_USERNAME` бота и
один раз выставить вебхук на публичный HTTPS-адрес (`setWebhook`, команда в документации).

## 3. Вне scope (в бэклог, требуют продуктовых решений или новых сервисов)

- Статус «пришёл/не пришёл», фактическая оплата, дашборд выручки (F10).
- Клиентская база, история по телефону, поиск и экспорт (F11).
- Несколько блокировок внутри дня (F12).
- Фоновая синхронизация DIKIDI вне рендера страницы (F14).
- Sentry/аптайм-мониторинг, CI и автотесты, E2E-набор (нужны внешние сервисы/инфраструктура).
- ICS-файл и ссылки «отменить/перенести» для клиента (отдельная фича поверх B1).
- Чекбокс согласия в форме — по решению пользователя не добавляем (2026-11-22).

## 4. План работ

1. **Этап 1**: транзакционный хелпер + атомарная запись, уведомление мастеру, pending-кнопка,
   единый источник цен на лендинге, событие конверсии, `/privacy` + футер + sitemap.
2. **Этап 2**: детали в карточке успеха, честные напоминания, проверка наложения в `/admin/new`,
   автообновление расписания.
3. **Этап 3**: rate limit логина, обязательный `CRON_SECRET`, канал `source`, метаданные `/book`,
   `not-found`/`error`/`loading`, настройки лимита и буфера.

После каждого этапа: `bunx tsc --noEmit` + проверки из таблицы этого этапа.
Малые диффы, каждый файл привязан к пункту спеки.

## 5. Риски

- Изменение `services` в рабочей БД: опечатка исправляется, дубль только деактивируется (`is_active=false`),
  строки не удаляются; у дубля 0 записей — потерять нечего.
- Рефакторинг главной в серверный компонент может сдвинуть вёрстку → проверка скриншотом до/после.
- Rate limit в памяти процесса не переживает рестарт и не общий для инстансов — для одного VPS достаточно,
  для serverless нужен внешний стор (в отчёте отмечено).
- Проверка Telegram реальной отправкой не выполняется (нет доступа к боту) — проверяется ветка no-op
  и код возврата; реальная доставка — за пользователем.
