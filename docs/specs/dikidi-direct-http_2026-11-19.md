# Спека и план: прямой доступ к DIKIDI без api-anything в проде

**Дата:** 2026-11-19 · **Проект:** `zaiko_ta/zaiko_ta_nextjs` · **Статус:** выполнено (итог внизу)

## Проблема

api-anything — локальный процесс: слушает `127.0.0.1:8787`, хранит cookie DIKIDI и описания операций
в `~/.api-anything`. На Vercel (serverless) его нет и быть не может: файловая система эфемерная,
loopback не тот, `--allow-writes` некому держать. Из-за этого синхронизация записей на проде
упадёт в `failed`, а пользователь увидит «api-anything не отвечает».

При этом api-anything для рантайма не обязателен: все шесть операций — обычные form-POST на
`https://dikidi.net/ru/owner/ajax/...` с cookie `token`. Значит, их можно вызывать напрямую из
приложения. Для локальной разработки api-anything остаётся как есть — переключается транспортом.

## Критерии приёмки

| # | Критерий (проверяемый) |
|---|---|
| 1 | При `DIKIDI_TRANSPORT=http` (или автоматически при наличии токена/кредов) чтение журнала, поиск/создание клиента, создание/обновление и удаление записи идут прямыми запросами к `dikidi.net`, без api-anything |
| 2 | При отсутствии доступа и `DIKIDI_TRANSPORT` не заданном поведение прежнее: используется api-anything, локальная разработка не ломается |
| 3 | Cookie `token` берётся из БД (`dikidi_auth`, обновляется автологином) или из `DIKIDI_TOKEN`; значение нигде не логируется |
| 4 | Есть автологин по `DIKIDI_LOGIN`/`DIKIDI_PASSWORD`: телефон → `auth.dikidi.net/ajax/check/auth/` → пароль → cookie `token` сохраняется в БД |
| 5 | Истёкшая сессия (редирект на вход / HTML вместо JSON) распознаётся как `unauthorized`, один раз выполняется повторный вход и повтор запроса; в интерфейсе причина видна текстом |
| 6 | Если DIKIDI требует капчу/SMS, возвращается понятная ошибка с указанием задать `DIKIDI_TOKEN` вручную — без «не отправлено» без причины |
| 7 | `npx tsc --noEmit` и `npx next build` проходят; локальный api-anything-путь сохранён и не изменён по поведению |

## Вне scope

Отказ от api-anything в локальной разработке, UI для ввода cookie, обновление `.env.example`
(env-файлы правит пользователь), повторные попытки по расписанию, работа с чужими компаниями.

## Решения

1. **Транспорт — переключатель, а не замена.** `lib/dikidi/api.ts` диспетчеризует `callDikidi()`:
   `http` — прямые запросы, `api-anything` — прежний клиент. По умолчанию `auto`: http, если есть
   токен (БД/`DIKIDI_TOKEN`) или пара `DIKIDI_LOGIN`/`DIKIDI_PASSWORD`, иначе api-anything.
2. **Токен живёт в БД** (`dikidi_auth`, одна строка `id = 1`): на serverless это единственное место,
   где обновлённая cookie переживёт инстанс. `DIKIDI_TOKEN` — запасной вариант/ручной ввод.
3. **Автологин — по факту истечения**, а не заранее: 401-подобный ответ → один вход → один повтор.
4. **Ответы прямой ветки отдаются в том же виде, что у api-anything** (`journal` → `.master`,
   остальные — как есть), поэтому `send.ts` и `availability.ts` не меняют логику разбора.

### Что осталось непроверенным

- Шаг пароля на реальном аккаунте DIKIDI (нет кредов) и прямой HTTP с настоящей cookie `token`
  (api-anything хранит её зашифрованной и наружу не отдаёт). Проверка после того, как пользователь
  впишет `DIKIDI_LOGIN`/`DIKIDI_PASSWORD` в `.env` (env-файлы агент не читает и не правит).
- Поведение с IP датацентра Vercel: возможен антибот-отказ DIKIDI — выяснится только на деплое.

### Отклонения

- Добавлена переменная `DIKIDI_BASE_URL` (по умолчанию `https://dikidi.net`) — понадобилась для
  проверки прямого транспорта на локальном моке без реальной сессии.
- `.env.example` не обновлялся (env-файлы правит пользователь); новые переменные описаны в `README.md`
  и таблице выше.

## Переменные окружения (добавляет пользователь)

| Переменная | Назначение |
|---|---|
| `DIKIDI_TRANSPORT` | `http` — всегда прямые запросы; `api-anything` — всегда локальный сервис; не задана — `auto` |
| `DIKIDI_TOKEN` | cookie `token` кабинета DIKIDI (ручной вариант, если автологин не проходит) |
| `DIKIDI_LOGIN` | телефон владельца кабинета для автологина (напр. `+375291234567`) |
| `DIKIDI_PASSWORD` | пароль кабинета DIKIDI для автологина |

## Риски

- Вход DIKIDI может потребовать SMS-код или капчу — тогда автологин не поможет, нужен ручной `DIKIDI_TOKEN`
  (код возвращает явную ошибку, а не молчит).
- DIKIDI может проверять IP: запросы с датацентра Vercel способны попасть под антибот. Проверяется только деплоем.
- Форма входа DIKIDI не документирована: при её изменении автологин перестанет работать, ручной токен останется.
- Cookie в БД — секрет в базе: доступ к БД = доступ к кабинету. Альтернатива — только `DIKIDI_TOKEN` в env.
