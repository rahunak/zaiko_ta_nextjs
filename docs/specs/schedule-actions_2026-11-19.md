# Действия с записями на странице расписания (`/admin/schedule`)

**Дата:** 2026-11-19 · **Тип:** фикс (2 файла + общий модуль) · **Проект:** `zaiko_ta_nextjs`

## Проблема

На `/admin/schedule` кнопки «Изменить»/«Отменить» были только у записей, созданных в админке.
Записи, которые пришли из журнала DIKIDI (`source = 'dikidi'`), оставались без действий — а именно
их видит мастер, если запись завёл клиент через онлайн-запись или сам мастер в кабинете.

## Сделано

| Что | Файл |
|---|---|
| Действия «Изменить»/«Отменить» для записей DIKIDI (`entry.source === 'dikidi'` и есть `dikidiId`) | `app/admin/(protected)/schedule/page.tsx` |
| Отмена записи DIKIDI: `remove-record` в кабинете, затем мягкая отмена связанной строки админки (если есть) | `app/admin/actions.ts` → `cancelDikidiAppointment` |
| Правка записи DIKIDI: связанная строка админки с `dikidi_id` + `sync_status='synced'`, дальше обычная форма правки (сохранение обновит ту же запись DIKIDI, без дубля) | `app/admin/actions.ts` → `claimDikidiAppointment` |
| Баннеры результата: «удалена из DIKIDI», «не удалось удалить + причина», расшифровка ошибок действий | `app/admin/(protected)/schedule/page.tsx` |
| Сборка адреса возврата с параметрами | `lib/url.ts` → `withQuery` |

### Попутно исправлено

`cancelAppointment` возвращал на `${backTo}?cancelled=…`, а `backTo` уже содержит `?date=…&range=…`.
Получалось `…&range=week?cancelled=5`: баннер не показывался, а вид переключался с «Недели» на «День».
Теперь параметры добавляются через `withQuery` (сохраняются `date`/`range`, кодируются пробелы и кириллица).

## Как работает правка записи из DIKIDI

1. Клик «Изменить» на записи DIKIDI → action `claimDikidiAppointment`.
2. Если строка с таким `dikidi_id` уже есть и не отменена — сразу открывается её форма правки (дубля нет).
3. Иначе создаётся строка `source='admin'`, `sync_status='synced'`, `dikidi_id=<id>`; услуга
   сопоставляется с `services` по имени (нет совпадения — остаётся название из DIKIDI).
4. Гонка двух кликов закрыта уникальным индексом `appointments.dikidi_id`: при `23505` открывается
   уже созданная строка.
5. В форме правки галочка уже подписана «Обновить запись в DIKIDI (та же запись, без дубля)» —
   сохранение идёт через `appointment_id`, DIKIDI обновляет запись, а не создаёт новую.

## Как работает отмена записи из DIKIDI

`cancelDikidiAppointment` → `removeDikidiRecord(dikidiId)` (транспорт из `callDikidi`).
Успех: связанная строка админки (если была) помечается `cancelled_at`, пользователь возвращается
на тот же день/неделю с баннером «Запись №… удалена из DIKIDI».
Отказ: запись остаётся, в адресе `removeError=<id>&reason=<текст>` — причина показывается в баннере.

## Проверено

- `npx tsc --noEmit` → 0; `npx next build` → 0 (сборка от 2026-11-19, 22:0x).
- `withQuery`: 6/6 (сохранение `date`/`range`, пропуск `undefined`, повторная запись параметра, кодирование кириллицы) — временный скрипт прогнан и удалён.
- Рендер `/admin/schedule` на своей сборке (`next start -p 3105`, временная сессия админа):
  неделя 19.11 — 8 записей DIKIDI с обеими кнопками; 26.11 — 2; 03.12 — 1; формы содержат
  `dikidiId`, `clientName`, `clientPhone`, `serviceName`, `startsAtIso`, `durationMin`, `price`,
  `backTo=?date=…&range=…` (один `?`), журнал DIKIDI загрузился (баннера об ошибке нет).
- Правка записи DIKIDI (POST server action, запись `1182668190`): создана строка id=4,
  `service_id=1` (услуга сопоставлена), `sync_status='synced'`, редирект на `/admin/appointments/4`;
  страница правки — 200, подпись «Обновить запись в DIKIDI (та же запись, без дубля)».
  Повторный клик → тот же `/admin/appointments/4`, вторая строка не появилась (в БД 1).
- Отмена несуществующей записи DIKIDI (`999999999`): редирект
  `/admin/schedule?date=2026-11-26&range=week&removed=999999999` — параметры не потерялись.
- Тестовые артефакты убраны: строка id=4 и временная сессия удалены, свой сервер на 3105 остановлен,
  временные скрипты/файлы удалены.

## Не проверено

- Реальное удаление существующей записи в DIKIDI через новую кнопку — это необратимое действие
  на живых данных, поэтому проверено только формирование адреса и ветка отказа.
- Ветка «не удалось удалить» с настоящим отказом DIKIDI (нет подходящей тестовой сессии).

## Замечено рядом (вне scope)

`lib/dikidi/source.ts` (`fetchDikidiSchedule`) по-прежнему читает журнал только через api-anything
(`callOperation`), в отличие от `availability.ts`/`send.ts`, переведённых на `callDikidi()`.
На Vercel без api-anything расписание покажет только записи админки — это надо закрыть перед деплоем.
